# dsh-replay

[English](README.en.md)

`dsh-replay` 为 DSH 提供输入历史回翻与用户消息重试。插件卡片名称固定为 `dsh-replay`，仓库为 `AutumnNazi/dsh-replay`，npm 安装名为 **`@bxzy/dsh-replay`**；**输入历史**与**消息重试**组件标题仍跟随 DSH 语言。

本文面向 `dsh-replay` 原生组件版，说明最新行为与使用方式；旧 `dsh-shuru` 的自建设置页说明不适用于本版本。

## 组件与语言

一个安装包包含两个原生 Cordis 组件：**输入历史**和**消息重试**。两者默认开启，可以在 DSH 的组件管理页分别启用或停用，互不依赖。

本版本没有自建设置页，只使用 DSH 原生组件开关。客户端通过宿主组件清单接口每秒同步一次启停状态，正常情况下开关约在 1 秒内生效（网络和清理耗时可能延长）；停用时会清理该功能实例，不只是隐藏按钮。不会读取、迁移或删除旧版保存在 `localStorage` 中的开关值，也不需要手动清理浏览器数据。

界面支持中文和英文，语言跟随 DSH，无需单独设置。

## 输入历史

- **仅当前会话**：历史按会话隔离，不跨会话共享。当前会话已发送的输入和旧用户消息都可作为历史来源，不把工具或运行时注入内容当作用户输入。
- **逐条回翻**：在输入框按 **↑** 浏览更早的输入，按 **↓** 返回较新的输入；越过最新一条后，恢复开始回翻前的草稿，包括引用内容。
- **保留原生编辑行为**：只有输入框为空或光标位于首行时，↑ 才尝试回翻；普通段落内的光标移动、输入法组合与宿主已消费的按键仍交给宿主。只有成功写回历史时才消费方向键。
- **定位文首**：写回历史后将光标定位到内容开头，便于继续按 ↑ 回翻或编辑；用户主动修改草稿时退出回翻状态。
- **旧消息逐页读取**：进入会话时读取已有用户消息，必要时通过 `loadOlder()` 补一页；回翻到最早已加载的条目后，仅在宿主表示还有更早消息（`hasMore`）时按需继续加载下一页，直到 `hasMore` 为 `false`。没有更多消息时不反复请求。
- **按需加载，不设默认条数上限**：原生组件逐页读取更早输入，不再因达到 100 或 2,000 条而停止回翻。不会在后台自动读取整个会话；内存随已加载历史与文本长度增长，停用组件时释放。能回翻的范围仍取决于 DSH 提供的会话记录。

历史保存在组件运行期间的内存中，不是独立的永久存档；旧输入能否回填取决于 DSH 可提供的会话消息。

## 消息重试

用户消息下方的操作行按时间、复制、重试的顺序显示。点击重试，将该消息的**文本**以 `queue` 模式作为新提问追加到当前会话。

- 不原地替换，不删除或修改原消息，也不重写已有回答。
- 只重新发送文本，不重复上传原消息中的图片或其他附件。
- 当前会话正在生成回答时，重试按钮不可点击。
- 发送失败时显示原因，不将失败当作成功；仍受 DSH 原生提交与权限控制约束，不绕过限制或自动提升权限。
- 停用消息重试组件后，撤销该组件的用户消息渲染接管，恢复 DSH 的宿主渲染；输入历史组件可以继续运行。

重试针对用户提问，也兼容部分来源标记缺失的旧用户消息；工具注入、运行时上下文和生成中的插话不提供重试。

## 安装与迁移

需要可用的 DSH 和 Node.js。**推荐使用 npm 安装名 `@bxzy/dsh-replay`**，以便当前插件管理器使用原生更新检测与用户确认流程。本地目录和 GitHub 仓库保留为手动源码渠道。

无作用域的 npm 包 `dsh-replay` 属于其他维护者，**不是本项目的包，请勿用它安装本插件**。

### 从旧版或 Git 来源迁移

如果已通过 `git+https://github.com/AutumnNazi/dsh-replay.git` 或其他 Git 来源安装同一插件，先由用户在 DSH 中**手动停用并卸载旧安装**，再添加 `@bxzy/dsh-replay`；发布 npm 包不会自动切换旧安装的来源。

旧 `dsh-shuru` 也应先停用并卸载。**不要同时启用旧包和新包**，否则可能发生快捷键与用户消息渲染注册冲突。本插件不替用户改配置，也不自动迁移旧开关值或数据；新包的两个原生组件默认开启。

### 从 npm 安装（推荐）

在 DSH 插件页点击“添加插件”，输入以下安装名，并按 DSH 提示完成 npm 安装：

```text
@bxzy/dsh-replay
```

安装后插件卡片仍显示 `dsh-replay`。保留 npm 来源，后续在该管理器中检查更新；GitHub 仓库地址不能替代 npm 安装名来获得当前网关的原生更新检测。

### 从本地目录安装（手动源码渠道）

```sh
git clone https://github.com/AutumnNazi/dsh-replay.git
cd dsh-replay
node scripts/build.mjs
```

在 DSH 的插件管理页选择从本地目录安装，选择克隆后的 `dsh-replay` 项目目录，并按 DSH 提示完成加载。

### 从 GitHub 仓库安装（手动源码渠道）

在 DSH 插件页通过“添加插件”输入以下仓库来源，并按 DSH 提示完成安装：

```text
github:AutumnNazi/dsh-replay
```

若要固定安装 v0.2.0，发布标签可用后使用 `github:AutumnNazi/dsh-replay#v0.2.0`。当前已核实的更新网关跳过 GitHub/Git 来源，不能通过它检测或确认这类来源的更新；后续版本需手动选择源码版本并按 DSH 提示处理安装与重载。

## 原生在线更新

通过 npm 来源安装 `@bxzy/dsh-replay` 后，在 DSH 插件管理页手动检查更新。当前已核实的管理器查询 npm 的 `latest` 版本；检查到版本差异后，由用户查看当前版本、可用版本，并在需要时打开 Release notes，然后点击更新以明确确认安装。点击更新会开始执行，不应期待额外的第二次确认；仅检查更新不会安装。

当前网关仅支持直接 npm 来源的更新检测与执行；GitHub/Git、本地目录和归档来源不走这条流程。此结论针对已核实的当前管理器，不概括所有 DSH 版本。GitHub Release 和附件不会触发 npm 更新检测，也不负责把旧 Git 安装迁移为 npm 来源。

本插件没有自建 `UpdatePanel`、更新 API、独立后台检查或新的设置页，不会自行静默安装。安装与重载由 DSH 原生管理器处理；以宿主报告的实际结果为准，失败时查看其错误与当前安装状态，不承诺跨卸载与重装的自动回滚。

**更新后复查启停状态**：当前更新网关以 `enabled: true` 执行安装，不能保证保留整个插件原先的停用状态；请复查输入历史与消息重试两个原生组件，并按需要分别启用或停用。两个组件与中英文字典随包保留，更新不需要额外设置页。

[v0.2.0 Release](https://github.com/AutumnNazi/dsh-replay/releases/tag/v0.2.0) 页面在发布创建后提供 `bxzy-dsh-replay-0.2.0.tgz` 与 `SHA256SUMS.txt`。下载后可用 SHA-256 对照校验文件；校验和用于检查文件完整性，不代替来源与包内容核验，也不会触发安装。

## 开发与检查

在项目目录执行：

```sh
node scripts/build.mjs
node scripts/check.mjs
node --test test/*.test.js
```

`build` 生成 `lib/` 客户端和入口产物；`check` 检查清单、补丁、构建产物与扩展面约束；`node --test test/*.test.js` 只运行 `test/` 下的自动测试，避免无边界扫描临时目录。不要把仅修改 `src/` 当作已更新安装包。

### Release 校验文件

发布维护者先用已有包管理工具打包，并核对归档中的包名为 `@bxzy/dsh-replay`、版本为 `0.2.0` 及发布文件白名单；不要把宿主源码、临时目录、依赖目录或凭据放入发布包。npm 发布通过包级 `publishConfig.registry` 指向 `https://registry.npmjs.org/`，无需改全局 registry。以下脚本仅读取已验包并生成校验文件，不打包、不安装、不发布：

```sh
node scripts/release.mjs --archive ./bxzy-dsh-replay-0.2.0.tgz --out ./release-assets
```

归档文件名必须为当前 `package.json` 对应的 `bxzy-dsh-replay-<version>.tgz`；版本变化后相应替换命令中的文件名。输出目录获得 `SHA256SUMS.txt`，归档保持原位；省略 `--out` 时写入本地临时发布目录。脚本不校验 TAR 内部内容，不能替代上面的包内容审查，也不会创建 GitHub Release 或运行 `npm publish`。维护者另行上传归档与校验文件到对应 Release；发布资产不纳入 Git。

## 本地构建更新如何生效

已加载的客户端 bundle 默认由 DSH 的 `client-hmr` 每 **500 ms** 轮询。重新构建后可等待更新通知；不必把每一次源码修改都当成必须完整重启。

首次安装，或修改包名、manifest、组件入口与补丁时，按 DSH 提示重新加载配置或重启。

若 bundle 更新没有生效，再尝试刷新界面并按宿主提示重载。

构建、检查与自动测试用于验证代码和产物，不等同于真实 DSH 环境的安装、原生组件管理页及界面验收。
